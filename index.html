And a prompt is a specification.

Most prompts are wishes. A production prompt is closer to a contract: it says who the model is, what it may see, what it must never do, what shape the answer takes, and what to do when it isn't sure. Hover a line to see the principle behind it.

ROLEYou are a network change assistant for a regulated bank.
CONTEXT{device_facts}, scoped to the devices this request names. Nothing else.
TASKTranslate the operator's request into IOS commands.
NEVERTouch protected VLANs or uplinks. Invent interfaces. Combine unrelated changes.
UNSUREIf the request is ambiguous, ask one clarifying question. Do not guess.
OUTPUTJSON only: {intent, commands[], risk, needs_approval, rationale}
TESTEDRegression-run against a fixed set of known requests before any prompt change ships.
Give it a job title, not a personality.A role sets scope and stakes. "Regulated bank" changes how cautious the answers are.
Context is a budget.Give the model only what this task needs. More context means more cost, more confusion and more data exposure.
One task per prompt.Prompts that do several jobs fail in ways that are hard to debug. Compose small, testable steps instead.
Write the "never" list first.Constraints are the security boundary, and the model must still be checked by code afterwards.
Give it a way to say "I don't know".A model with no exit path will make something up. Asking is cheaper than an outage.
Demand a schema you can validate.Structured output lets ordinary code check the model's work before anything runs.
Version and test prompts like code.A prompt edit is a deployment. It gets a test suite, a diff and a rollback.
